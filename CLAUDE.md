# Rules
- Only mark a TODO item done when a test exists and passes for it
- Never delete a TODO item. `TODO.md` holds only open / in-flight work; `DONE.md` is the archive of completed and decided (out-of-scope / not-reproducible) sections, split by topic into `DONE/*.md` files (see `DONE.md`'s index/table for which file covers what — it's an unbounded archive, so it doesn't live in one file). When a `## ` section in `TODO.md` is fully closed — every item `[x]`, or the remaining `[ ]` items are explicitly N/A — move the whole section verbatim (heading + items + notes) into the matching `DONE/*.md` file, preserving its text. Archiving is the mechanism for "never delete"; nothing is removed, only relocated
- Solo project: commit directly to `main`. Don't create feature branches for commits
- `cargo build` and `cargo test` must both be warning-free before a task is done (a `pub` item only reached from `#[cfg(test)]` code warns in the non-test build — gate it `#[cfg(test)]` or remove it), `cargo fmt --check` must pass, and `cargo clippy --all-targets -- -D warnings` must be clean — CI and the pre-push hook (`.githooks/pre-push`) both enforce all three, so a task isn't done until all three pass locally, not just build+test
- `cargo test` runs the full suite (~1955 tests, ~4s as of 2026-08-22) — still pass an explicit long timeout (900000 ms) rather than the tool default, since a cold `cargo build` of the dependency tree (~2.5 min, see the dev profile below) can precede it. Two build settings plus one test-harness setting keep it there and must not be dropped: `.cargo/config.toml` sets `LIBSQLITE3_FLAGS=SQLITE_DEFAULT_MEMSTATUS=0`, without which SQLite's global allocation-statistics mutex serialises every test thread (the suite took 658s, and got *slower* the more test threads it was given); `Cargo.toml`'s `[profile.dev.package."*"]` builds dependencies — chiefly the bundled SQLite C library — at `opt-level = 2` while this crate stays at 0, so incremental rebuilds stay fast. The third is `test_support::test_pool`'s cached schema (see Test conventions): replaying the 48 migration files cost ~89 ms per pool against ~1500 pools, ~220 s of CPU that the parallelism was hiding behind a 23 s wall clock. Each file carries the reasoning; if the suite ever looks slow again, check all three are still in effect
- Building needs `protoc` on the machine (the `yfinance-rs` dep's build script compiles a protobuf schema): `brew install protobuf` locally, and ci.yml installs `protobuf-compiler` — keep that step if the workflow changes
- CI also gates the dependency tree: `cargo deny check advisories` fails on known RustSec advisories (config + policy in `deny.toml`; run the same command locally — `cargo install cargo-deny --locked`). An advisory with no upstream fix goes on deny.toml's ignore list with a `reason` and a same-line `# expires: YYYY-MM-DD` comment; `doc_checks::advisory_ignores_expire` fails the suite once the date passes, so ignores are always temporary. Dependabot (`.github/dependabot.yml`) raises weekly grouped update PRs for Cargo and GitHub Actions
- Implement a requirement fully: if the spec says "apply the 50% CGT discount", compute the discounted figure — don't stop at an eligibility flag/indicator. If only partially done, leave it unchecked in TODO with a note on what remains
- Recurring background tasks (weekly backup, weekly RBA FX import, monthly imports, future jobs) run via the cron scheduler in `infra/scheduler.rs`: register the work in `registry()` (`infra/scheduler/registry.rs`) and add a line to `schedule.cron`. A schedule line may carry an optional IANA timezone between the cron expression and the job name (`30 17 * * 1-5 America/New_York price-import`) — use the market's own zone for market-close-driven jobs so DST can't shift the margin over the close; no zone means local server time. The scheduler logs the next scheduled run time at INFO after every run (and at startup) — its `next run scheduled` line — so the schedule is verifiable from logs without reading code. Every run also goes through `run_job`, which brackets it with `job started` / `job finished` INFO lines; keep both the scheduled loop and the manual `POST /jobs/{name}` trigger routed through it so no job bypasses the start/finish logging or the per-job lock that serialises runs of the same job (an overlapping trigger waits for the in-flight run, never executes concurrently)
- Keep the docs in sync when the data model or HTTP API changes: a new/changed table or column updates `docs/SCHEMA.md` (incl. its Relationships section); a new/changed/removed endpoint, status code, or request/response shape updates `docs/API.md` (incl. its Response codes section); a user-visible feature or scope decision updates the Features or Known limitations list (`README.md` / `docs/API.md`). Doc updates are part of the same task, not a follow-up

# Financial correctness
- ATO reference guidance is mirrored in `docs/ato/` (CGT calculation, the 50% discount and loss-netting order, cost base, AMIT/AMMA cost-base adjustments incl. CGT event E10, LIC deduction, managed-fund income components, the FITO offset limit). Read `docs/ato/OVERVIEW.md` first — it indexes each file and maps it to the relevant calculation. Consult these before implementing or changing any tax rule; the live ATO site (ato.gov.au) is authoritative if a doc looks stale
- To fetch from ato.gov.au use `scripts/ato-fetch.py URL` (add `--examples` for just the worked-example sections) — the site returns 403 to non-browser clients, so the WebFetch tool does not work; the script fetches via curl with a browser User-Agent and strips the HTML to text. The ATO legal-database print view (`https://www.ato.gov.au/law/view/print?DocID=<DOCID>&PiT=99991231235958`) renders a whole publication in one page. Mirror anything you rely on into `docs/ato/` (source URL + retrieval date header) and index it in `docs/ato/OVERVIEW.md`, escaping every `$` in the mirrored prose as `\$` (GitHub renders a pair of them on one line as a LaTeX span, swallowing the quoted text between); that is a rendering escape only, so normalise it back before comparing a mirror against its live page — `doc_checks::ato` is what does that for the tests
- Money and quantities are always `Decimal`, never `f64`. New monetary columns are `TEXT`; migrations must preserve precision (never round-trip a value through a `REAL` column)
- `TEXT` decimal columns cross the sqlx boundary through `infra::decimal`'s `Money`/`OptMoney` newtypes in *both* directions: a row struct is `#[derive(sqlx::FromRow)]` with `#[sqlx(try_from = "Money")]` / `#[sqlx(try_from = "OptMoney")]` on its plain `Decimal`/`Option<Decimal>` fields, and a write binds `.bind(Money(x))` / `.bind(OptMoney(x))`. Never hand-write a `FromRow` for a row struct a derive can express, and never `.bind(x.to_string())` (a test scans for it) — the read half is compiler-enforced, since `Decimal` has no `sqlx::Type<Sqlite>` impl of its own. `row_dec`/`row_opt_dec` (same codec, column named by sqlx) are for the two `FromRow` impls a derive *cannot* express — a tagged enum whose payload columns vary by variant (`ActionKind`), a struct with computed fields (`reports::performance::TradeFlow`) — and for ad-hoc row reads; `parse_dec` is for a `String` already in hand. Parse failures always propagate as `sqlx::Error::Decode`; never `.parse().unwrap_or(Decimal::ZERO)` — a silent zero corrupts financial output without failing
- Reports take the Australian-tax view: cost base, proceeds, and income totals are in AUD. Convert every non-AUD amount to AUD using the record's `fx_rate` before aggregating or comparing — never mix currencies in one calculation
- Market settlement (T+n) counts business days — skip weekends and the exchange's seeded public holidays (`exchange_holidays`, looked up per the listing's exchange via `exchange_holiday::exchange_holidays_for_listing`); never just add calendar days. Exchange-less listings (`security_type = 'Crypto'`, NULL `exchange_mic`) settle same-day instead — no T+n, no holiday calendar (`trade::auto_settlement_date`)

# Data integrity
- A transaction that **writes** is begun with `infra::db::write_tx(pool)` — `BEGIN IMMEDIATE`, which takes SQLite's write lock at the `BEGIN` — never with `pool.begin()`. A deferred `BEGIN` starts as a reader and fails *immediately* when it tries to upgrade after another connection has written (`SQLITE_BUSY` 5 / `SQLITE_BUSY_SNAPSHOT` 517, neither of which `busy_timeout` retries), which is a 500 with an empty body for whoever was writing; queued from the start, the busy timeout applies and a concurrent writer waits its turn. Read-only transactions stay on `pool.begin()` (see the reports bullet). `infra::db::tests::write_side_modules_never_begin_a_deferred_transaction` scans `src` for a deferred `BEGIN` and names the read-only report files one at a time in its allowlist, so a new report file is an offender until it is classified. Top-level only: sqlx issues a `SAVEPOINT` for a nested transaction and rejects a custom `BEGIN` there, so a transaction on an existing `&mut *tx` keeps using `.begin()`
- Enforce data-model invariants at write time inside a transaction, not only in reports. A multi-row invariant (e.g. a Sell's parcel allocations must sum to its quantity) must be validated and committed atomically so a partial/invalid state can never be persisted; reject with `422` otherwise. If standalone child-entity writes could reintroduce a bad state, restrict them
- Every field in the data model must be used by a calculation or endpoint, or carry a comment marking it informational-only. Don't leave stored fields silently unused
- Migrations must never drop data: no destructive schema changes — migrate existing rows forward (e.g. the holding-accounts migration moved every row to the seeded default account)
- A field that holds a limited set of values is an enum: CHECK-constrained in the database (and a typed enum where parsed in Rust), never a free-text column
- Every UPDATE/DELETE of an audited table is recorded by the append-only audit trail (`row_history`, migration 0013; inspected via `POST /reports/row_history` and the web UI's Row History screen). The audited-table list lives in three places a test pins together: the migration's CHECK + trigger pairs, `reports::row_history::AUDITED_TABLES`, and the UI table picker in `config.js`. A migration that adds a column to an audited table must DROP and re-CREATE that table's two `*_row_history_*` triggers with the new column list; a new financial fact table needs its own trigger pair plus entries in all three lists. Never UPDATE or DELETE `row_history` itself (its own triggers abort the write) — retention is keep-forever by decision

# Project structure
Modules are grouped into four folders; `main.rs`, `app.rs`, and the migrations live at the `src` root.
- `src/main.rs` — server startup: init pool, build registry, spawn scheduler, serve, graceful shutdown
- `src/app.rs` — `app::router(pool, registry, fetcher)` assembles entity + report + scheduler routers (testable without `main`). The price `fetcher` (`closing_price::SharedFetcher`) is injected, not constructed here, and `scheduler::registry(pool, db_path, fetcher)` takes it the same way — the live `YahooFetcher` is built only in `main`, so no test path can reach the network (tests pass `closing_price::test_support::QuoteStub`)
- `src/ato_examples.rs` — `#[cfg(test)]`-only acceptance tests reproducing the worked examples in the ATO docs (`docs/ato/`): each test cites its doc + example, enters the facts purely via the HTTP API (full `app::router`), and asserts the ATO's stated figures. Add a test here when a new feature makes another doc example representable
- `src/doc_checks.rs` — `#[cfg(test)]`-only tests pinning documentation-only requirements (a TODO item is only done with a passing test, including doc-only items): each asserts its required text — e.g. a Known-limitations entry and the QC header of the ATO doc it cites — is present in `docs/API.md`/README via `include_str!`. Add a test here when a requirement is satisfied by documentation alone. One test in the file is structural rather than textual: `every_markdown_link_resolves` walks **every** `.md` in the repo at runtime and fails on a relative link whose file is missing or whose `#fragment` names no heading — the archive is maintained by *moving* whole sections between files, and a link written relative to the repo root breaks when its section lands in `DONE/` (`docs/API.md` becomes `../docs/API.md`). Anchors are compared on GitHub's `github-slugger` rule, which does **not** collapse repeated separators: an em dash is stripped and leaves both surrounding spaces, so `## A — B` is `#a--b`, not `#a-b`. A moved section fixes its own links; a bold lead-in like `**Ticker or name changes:**` is not a heading and cannot be linked as one
- `src/infra/` — cross-cutting infrastructure (`mod.rs` re-exports each):
  - `infra/db.rs` — pool init (runs migrations), `write_tx` (the `BEGIN IMMEDIATE` every write transaction is begun with — see Data integrity), weekly DB backup (`backup`/`backup_path`): each fresh backup is verified (`PRAGMA integrity_check` + migrations match the live DB; a bad file is quarantined as `<name>.db.bad` and the job fails loudly), then the destination is pruned to the retention policy (newest 8 + first-of-month keepers for the 12 most recent months; only pattern-matched backup files of this database are ever deleted). Off-machine copies are deliberately a documented external step (README "Off-machine copies"), not a job
  - `infra/args.rs` — CLI args: `--db` (default `share-tracker.db`), `--port` (default 3000), `--schedule`
  - `infra/logging.rs` — tracing subscriber init; reads `RUST_LOG`, defaults to `info`
  - `infra/decimal.rs` — the `Money`/`OptMoney` TEXT⇄`Decimal` sqlx codec (`Type`/`Decode`/`Encode` for Sqlite), plus the `parse_dec`/`row_dec`/`row_opt_dec` helpers over it
  - `infra/fx.rs` — AUD conversion via the ATO/RBA reference rate (per-trade `fx_rate` fallback): `FxRates` pre-loads the whole rate table so report loops convert from memory — reports load it once (inside their read transaction) instead of one DB lookup per row (the pool-based `to_aud`/`resolve_rate` twins are `#[cfg(test)]`, kept to pin that both paths resolve identically). `resolve_valuation_rate` (pool and `FxRates` forms) is the **valuation-only** fallback: when the valuation month's rate isn't imported yet it substitutes the most recent earlier month's (≤ 2 months back) and flags the result provisional — only snapshot generation, live-quote conversion, and the period-performance report's FX attribution (`reports::period_performance`, over `reports::valuation::stored_valuations`) may call it, and the caller must surface the flag (snapshot `provisional`, row `fx_provisional`, period-performance `provisional`); tax calculations and FY reports stay on the strict path so no tax figure is ever computed from a fallback-month rate
  - `infra/http.rs` — `ApiError`, the one error type every handler returns (`Result<_, ApiError>` + `?`): `Internal` responds 500 with an empty body and logs the wrapped error via `tracing::error!` when the response is built — never `map_err(|_| StatusCode::…)`, which swallows the cause; `Unprocessable`/`BadRequest`/`not_found(msg)` carry the plain-text reason the web UI shows. `From<sqlx::Error>` classifies DB constraint violations as 422 with the rephrased constraint message — its foreign-key wording is the **write** direction ("the request refers to a record that does not exist"), so a DELETE must never reach that arm: a delete fails the same FK for the opposite reason (the row is there and something depends on it) and classifies the violation itself via `fk_dependants_message`, which discovers the blocking tables from `PRAGMA foreign_key_list` and answers a 422 naming each with its row count. `delete_handler` does this for every `CrudEntity`; a hand-written delete with its own outcome enum carries the ready-made body in a `StillReferenced(String)` variant so the wording still lives in the `From<EntityError> for ApiError` arm (see `entities::corporate_action::db::DeleteError`). Per-entity error enums stay and convert via `impl From<EntityError> for ApiError` beside the enum — handlers never match error variants themselves. Every error enum in the tree is `#[derive(thiserror::Error, Debug)]` with an `#[error("…")]` per variant, `#[from]` on its `Db(sqlx::Error)` variant (so `?` converts and never a hand-written `impl From<sqlx::Error>`), and `#[source]` on a variant wrapping another error enum — that keeps the underlying failure's own message in `Display` and reachable through `source()` when the enum ends up inside `ApiError::Internal`. The `#[error]` strings are **log** wording, deliberately not the user-facing 422 bodies: those live in the `From<EntityError> for ApiError` arms, which `docs/API.md` documents and per-entity rejection tests pin. Four `From<sqlx::Error>` impls stay hand-written for stated reasons — `ApiError`'s (it classifies constraint violations rather than wrapping) and the three report enums whose `Db` arm is a `String` carrying non-sqlx failures too (`reports::valuation`/`snapshot`/`period_performance`)
  - `infra/scheduler.rs` — maintenance-job registry, cron parsing/spawn, inspection routes. Split the same way as `trade.rs`: the parent is re-exports (every `scheduler::X` path preserved, test-only ones behind `#[cfg(test)]`) plus the inline test module, over `src/infra/scheduler/` — `registry.rs` (what each job name does, plus `JobParams`/`RegisteredJob`/`JobTrigger`; add a job with one `register(&mut jobs, "name", …)` call taking an async closure — or `register_manual` for a deliberately schedule-less one-off repair — never by hand-rolling the `Arc`/`Box::pin` wrapping. `register` means the job expects a line in `schedule.cron`, and `schedule::spawn` warns at startup when it has none; `register_manual` records the opposite intent so that warning only ever means a lost line, and `GET /jobs` carries the same flag as `trigger`), `schedule.rs` (`parse`/`spawn` over `schedule.cron`), `run.rs` (`run_job`, the per-entry timer loop, `next_run`), `db.rs` (the bounded `job_runs` history), `http.rs` (`GET /jobs`, `POST /jobs/{name}`)
- `src/domain/` — domain calculations shared by entities and reports, where divergence between callers would be a correctness bug. `domain/cost_base.rs` is *the* adjusted-cost-base pipeline (initial cost pro-rated to the costed units → AMIT per-unit reduction over the units the adjustment row covers, per CGT event E10 → return-of-capital per-unit reduction per G1, split-aware, both floored at nil → AUD conversion at the acquisition month via `CostBase::into_aud_with` over pre-loaded `infra::fx::FxRates`), carrying the ATO citations; the realised/unrealised/portfolio/open-parcels reports and the scrip-exchange/demerger/transfer operations all call it — never re-implement the pipeline inline. Both reductions are stated **per unit**, so the caller must say what became of the units it is costing: `adjusted_cost_base`/`adjustment_detail` take a `Held` enum (`AsAt(Option<date>)` for units still held, `DisposedOn(date)` for a sale allocation), which bounds the payments they were held for *and* decides which side of an AMMA statement's year end they sit on — never collapse the two back into one `Option<NaiveDate>`. Its `ParcelRow` is the shared `FromRow` mapping of a Buy/DRP trade row — reports select `ParcelRow::columns()` (or `columns_qualified(alias)` where the query joins another table) rather than re-mapping trade columns field-by-field; the list is a function, not a column const, because the mapping's last two fields are derived rather than selected — a demerger's head listing, off `corporate_actions`, which is what tells its head replacement parcel from its spun-off one, and `registered_from`, a recursive walk back up the rollover chain to the date the units joined this listing's register — and a caller that selected only the `trades` columns would silently lose both, each of them a return-of-capital entitlement bug. `domain/open_parcels.rs` is the loader *around* that pipeline: `load(conn, as_of)` reads the Buy/DRP rows, the sale allocations, the AMIT/ROC/split events and `FxRates` on the caller's own connection (so it composes into the report's single-snapshot read transaction), drops the fully consumed parcels and returns each open parcel's `ParcelRow` + remaining quantity in `as_of`'s unit basis + AUD `CostBase` — every open-holdings view (portfolio overview, unrealised gains, the open-parcels schedule) is built on it, and a new one must be too rather than re-assembling the read. Its `db_units_sold(conn, as_of)` is the allocations read on its own, for the walks that need per-sale dates instead of a remainder (performance, the net-capital-gain report's per-cohort E10/G1/C2 walk, and `amit_adjustment::db_cost_base_reduction_events`, which needs the units disposed of by each statement's year end). `domain/rollover.rs` is the shared machinery of the three parcel-substituting *operations* (scrip exchange, demerger, transfer), which are not built on `open_parcels` because a replacement parcel carries its cost base forward in the original's own currency, not AUD: `CostBaseInputs::load(conn, listing_id)` + `carried_cost_base`/`open_parcels` (the per-listing remaining-units walk over `domain::cost_base`), `closing_sell_body`, `insert_replacement_buy` with its `Provenance` column enum, and `created_trades`. A new operation of that shape uses these rather than growing its own copy of the walk or the INSERT. Its closing Sell goes through `sell::upsert_sell_in_tx(conn, SellWrite { .. })`, whose `provenance` is the twin enum on that side (`sell::SellProvenance`, two variants wider — a buy-back participation and a worthless-shares recognise close parcels without substituting any): a Sell belongs to exactly one operation, so a new one adds a variant to it and to the INSERT's column mapping rather than another `Option<i64>` parameter. `domain/tax_year.rs` holds `tax_year_for` — *the* Australian financial-year bucketing rule (July = next FY, identified by the calendar year of its 30 June end); every FY-keyed report (tax summary, net capital gain, E4 cross-check) uses it — never re-derive `month() >= 7` inline
- `src/entities/<entity>.rs` — one file per domain entity, CRUD + write-time invariants (see pattern below). `entities::router()` (in `entities/mod.rs`) merges them all. Three entities outgrew one file, split the same way: `trade.rs` is the parent (re-exports + the inline test module) over focused submodules in `src/entities/trade/` — `model.rs`, `checks.rs` (write-time checks shared with the Sell path), `settlement.rs`, `db.rs`, `http.rs`; `corporate_action.rs` likewise over `src/entities/corporate_action/model.rs` (the `ActionKind`/`CorporateAction`/`CorporateActionBody` types), `db.rs` (CRUD + the referenced-by-trade write-time check), `http.rs` (routes), `adjustments.rs` (the ROC/split cost-base-adjustment events and pure re-basing math, consumed by the reports and write-time checks). `closing_price.rs` likewise over `src/entities/closing_price/` — `model.rs` (the stored row and its `status`/`origin` enums), `market.rs` (the listing-plus-exchange-calendar context, a *timeline* of identities, every dated question asked of the one in force then), `fetcher.rs` (the `PriceFetcher` trait and the two provider-agnostic pieces over it: `CachingFetcher` and `clean_price`), `yahoo.rs` (the live implementation — everything provider-specific, so the trait stays the swap point), `db.rs`, `held.rs` (the held-days timeline collection is scoped to), `collection.rs` (the fetch-and-store path the scheduled job, manual re-fetch and backfill share), `live.rs` (on-demand live valuation), `http.rs`. It is also the one whose **tests** outgrew the parent, so they are a directory too — `closing_price/tests/mod.rs` holds the fixtures more than one topic uses (the builders, the `StubFetcher` provider double, the router/JSON helpers) over one file per subject (`market`, `held`, `collection`, `live`, `fetch`, `manual`, `unpriced`, `delete`, `schema`, `price_basis`, `fetcher`, `yahoo`); a fixture only one topic calls lives in that topic's file, and each file opens with `use super::*` so the glob chain to the entity is unchanged. Split an entity's tests the same way only once the parent is mostly tests — and split the *code* first, in its own commit, so the untouched tests are what proves that split. `closing_price::test_support` (the report tests' `QuoteStub`) is its own file beside them. In all three, every `entities::<name>::X` path is preserved by re-export (test-only-external items re-exported behind `#[cfg(test)]`, matching `trade.rs`'s `UpsertError`), so callers are unaffected. Split another entity the same way once it reaches a similar size (as a rule of thumb, once the combined parent + submodules would match `trade`'s/`corporate_action`'s ~3000 lines). Two file-name allowlists have to follow a moved call site: `infra::fx`'s `VALUATION_RATE_CALLERS_ALLOWED` and `infra::db`'s `DEFERRED_BEGIN_ALLOWED` — a split that moves one of those calls into a submodule fails their scan until the entry names the new path
- `src/reports/<report>.rs` — read-only AUD aggregations (portfolio, realised/unrealised gains, tax summary). `reports::router()` (in `reports/mod.rs`) merges them all. A multi-query report reads all its inputs on one `pool.begin()` read transaction (a single consistent snapshot — an interleaved write must never produce e.g. an allocation whose parcel is missing from the same read) and pre-loads FX via `FxRates::load` inside it; keep new reports on that pattern, and add the new file to `DEFERRED_BEGIN_ALLOWED` (see Data integrity), which is what says it is a reader. The one exception to read-only is `reports/snapshot.rs`, which persists the price-dependent reports' daily results to `report_snapshots` — so its write transaction is begun with `infra::db::write_tx`, like any other write. Snapshot staleness is *not* invalidated from Rust — the schema's staleness triggers (0001_schema.sql) stale snapshots inside every fact write's own transaction — so a new dated fact table (or a new date column on one) needs a matching set of staleness triggers in a migration, unless no snapshotted report reads the table (then say so in the migration, as 0006_rights_sales.sql does). That set is pinned the way the audited-table list is: `reports::snapshot`'s `every_table_is_classified_for_snapshot_staleness` test enumerates the live schema's tables and requires every one to be classified — either in its triggered list, carrying exactly the `*_stale_snapshots_*` triggers named there, or in its exempt list with the reason a write to it can invalidate no snapshot (the reason its migration gives). A new table in neither list fails the test, so classify it there in the same task
- `src/web.rs` + `src/web/{index.html,app.js,chart.js,config.js,forms.js,nav.js,taxreport.js,util.js,style.css}` — the web frontend: a no-build-step single-page app (plain HTML/CSS/JS as native ES modules, `<script type="module">`) embedded with `include_str!` and served by `web::router()` (`GET /`, `/static/style.css`, and one `/static/*.js` route per module via `JS_MODULES` — a new module needs its `(route, include_str!)` pair there, and a test asserts every import specifier resolves to a served route), merged in `app::router`. The module graph: `app.js` (the entry point — generic list/form/report/action views, `filterableTable`, the hash router) imports `config.js` (the `ENTITIES`/`REPORTS`/`ACTIONS` configuration), `forms.js` (field constructors, `buildFieldInput`/`readFieldValue`, the GST/income form-wiring hooks, `allocationEditor`), `chart.js` (the inline-SVG time-series graph — `seriesChart` — plus the pure helpers driving it, `presetRange`/`sliceSeries` for its date range and `chartWidth`/`weekTicks` for its geometry, used by the Portfolio Overview screen's performance panel; the graph is built at its holder's **measured** width rather than at a fixed viewBox, because the SVG scales uniformly — a fixed drawing stretched across a wide window would zoom its axis type and stroke weights with it — so `app.js` redraws it from a `ResizeObserver`, and its x axis is a weekly calendar grid dated as densely as that width allows), `nav.js` (the top menu bar's config-driven model and rendering), `taxreport.js` (the Annual Tax Report's own renderer — see the `filterableTable` exception below), and `util.js` (DOM/API/formatting helpers, the `COLUMN_KINDS`/`COLUMN_LABELS`/FK-naming maps, exact decimal-string arithmetic). The app is config-driven — each entity is described once and generic list/form code drives the existing JSON API; do not add a parallel data path. When you add/change an entity, report, or its fields, update the matching `ENTITIES`/`REPORTS` config entry in `config.js`. A parameterised report (the parcel optimiser, the pre-sale what-if) is still one `REPORTS` entry: `params` declares its submit-to-run form as forms.js field constructors, and `tables` renders an object response as titled tables per configured key — use these for new input-taking reports rather than a bespoke view. Post-record actions (reinvest, exercise, participate, scrip exchange, demerge, generate-adjustments) are likewise one `ACTIONS` config entry each, rendered by the generic `viewAction` — add new owner-row actions there, not as bespoke views. An action needing the user to confirm something the server computes (the AMMA statement's AMIT-adjustment generation, previewed against the statement's units held) declares `confirm: fn(path, body) -> Promise<bool>` — an async gate `viewAction` runs with the assembled body before the POST, false cancelling the submit — rather than a bespoke submit path. Parcel-allocation rows (Sell, Transfer, Participate) come from the shared `allocationEditor` helper, and an entity whose form should show only the selected type's fields (e.g. corporate actions) declares `typeField`/`fieldGroups`/`typeDescs` (and optionally `typeLabels` for per-type common-field labels) on its config. All data tables (entity lists, the Sells list, report tables) render through the shared `filterableTable` so they are uniformly filterable + sortable; route new tables through it rather than building a bespoke `<table>`. Two behaviours are derived *there* from the column **names**, so a new table inherits both with no wiring: a cell naming a listing (`listing_id`, `scrip_listing_id`, `demerger_listing_id` — `util.js`'s `FK_LINK_ROUTES`, keyed off the same `FK_COLUMN_SOURCES` that gives the cell its label) links into that listing's activity ledger, suppressed by `opts.selfRoute` on the screen it would point back at, and a table that composes a listing name for display instead of showing the FK cell (the Closing Prices screen, the price-health surfaces) asks for the link by column name via `listingLinkFrom`; and every table opens **newest-first** on its first date column (`defaultSortColumn` — `date`/`date_*`/`*_date`/`*_at`; a table with no date column keeps the server's order). No table opts out: where the sort key ties the rows reverse with it, so a descending sort is the exact reverse of the ascending one, which is what lets a table carrying a running total (the activity ledger's `units_after`) read newest-first with its balance still stepping monotonically down the page — don't reach for a per-table ordering flag, fix the tie-break. The one deliberate exception is the Annual Tax Report (`custom: 'tax-report'` in `config.js`, dispatched to `taxreport.js`'s `viewTaxReport`): a print document meant to be saved to PDF and archived, where `filterableTable`'s filter row, sort indicators, and — critically — its 50-row pager (which would silently print only the first page) have no business; it renders plain semantic `<table>`s instead, formatted through the same `numericDisplay`/`columnLabel` helpers so figures still read identically to the rest of the app, over a dedicated `@media print` block in `style.css`. Numeric columns are display-formatted by `filterableTable` per a name-keyed `COLUMN_KINDS` map in `util.js` (money → 2 dp + thousands grouping with the full value on hover; rates/quantities verbatim; average price figures (derived or entered) rounded to 4 dp with the full value on hover) — classify a new numeric column there, don't format in a view. That map governs table *cells*; money written into **prose** (a health-banner sentence, a confirm dialog, a toast) goes through `util.js`'s shared `moneyText`, never concatenated straight in — a `web.rs` scan test fails a `COLUMN_KINDS` money name written into a string without it, and both halves of the rule are what keep a figure reading the same wherever it appears. UI items are tested by asserting the view + the API path it drives appears in the served bundle — the concatenation of every served JS module (`app_js_body` in `web.rs`) — with no browser harness. A list the UI **copies** from the server is never asserted by transcribing it into a test: every `sel()` option list in `config.js` is pinned to the definition it copies by `select_option_lists_are_pinned_to_their_server_side_source` — the live schema's own `CHECK (<column> IN (…))` read out of `sqlite_master` for a stored enum (`security_type`, `cost_base_rule`, `income_type`, `expense_type`, `residual_handling`, `action_type`, `worthless_event`), the Rust const for the two that are stored nowhere (`table` → `reports::row_history::AUDITED_TABLES`, `strategy` → `parcel_optimiser::ALL_STRATEGIES` through serde), and a stated subset for the one that is deliberately narrower than its column (`trade_type`, Buy only) — and a picker in none of those lists fails the test, so a new one is classified there rather than growing a hand-written copy in a test. The same shape covers the health banner: every field of `reports::health`'s serialised report must be read as `h.<field>` inside `refreshHealthBanner`, or be classified in that test's `HEALTH_FIELDS_SURFACED_OFF_THE_BANNER` with the read that surfaces it instead (`unpriced_days`, listed on the Closing Prices screen with its backfill action), so an alert cannot be computed on every page load and shown to nobody. The pure helpers in `util.js` (display rounding/grouping/padding, the exact decimal-string arithmetic) and `chart.js` (`presetRange`/`sliceSeries`, `chartWidth`/`weekTicks`) are additionally unit-tested by `src/web/*.test.js`, run with `node --test 'src/web/*.test.js'` (Node 22+, no build step — `src/web/package.json` marks the tree as ES modules so Node parses them as the browser does); test files can never be served because `JS_MODULES` is an explicit allowlist, and a `web.rs` test pins the partition (no `*.test.js` on the route table, every non-test module on it). `scripts/ui-smoke.sh` is the CI headless smoke check (server on a temp DB + demo fixture; key hash routes must render seeded data in headless Chrome — catches a broken module route or load-time exception the bundle assertions can't); ci.yml runs the Node tests and the smoke check alongside the cargo checks. For a manual visual/DOM spot-check there's `scripts/ui-check.sh` (zero-dep: ephemeral server on a temp DB + free port, optional `--seed <fixture>` from `scripts/fixtures/`, then headless Chrome `--dump-dom` or `--screenshot` for given hash routes, all torn down on exit) — e.g. `scripts/ui-check.sh --seed demo '#/r/open-parcels'`. `scripts/ui-drive.js` is its interactive counterpart for a check a rendered DOM cannot answer (clicks, typing, hovers, native `confirm()` text, print-media emulation, console/exception capture): a zero-dependency Chrome DevTools Protocol driver over Node's global `WebSocket`, run as `node scripts/ui-drive.js --url <server> steps.js`. Like `ui-check.sh` it automates a manual spot-check and is deliberately not a browser test harness — neither runs in CI. `scripts/screenshots.sh` is the one scripted use of that driver: it regenerates the README's screenshots into `docs/screenshots/` (server on a temp DB seeded from `scripts/fixtures/showcase.json`, a wholly fictional portfolio — never the real one), capturing each view twice via `scripts/screenshots.steps.js`, once per colour scheme, because the README pairs them in a `<picture>` element that follows the reader's GitHub theme. Re-run it and commit the PNGs when a captured screen changes
- `migrations/NNNN_description.sql` — sqlx migrations, applied once in order by `infra::db::init()`

# Domain entity module pattern
Each entity in `src/entities/<entity>.rs` follows this structure:
1. Model struct — derives `Serialize`, `Deserialize`, `sqlx::FromRow`
2. Input body struct — for PUT endpoints; omits the primary key (comes from URL path) — and carries `#[serde(deny_unknown_fields)]`, as **every** struct deserialised from an inbound request does (`Json`/`Query`/`Form` bodies, report requests, operation bodies): a misspelt field name must be a `422` naming it, never a silently-ignored default writing a zero into a tax figure. `infra::http::tests::every_request_body_denies_unknown_fields` walks every type reachable from a handler's extractor and fails on one that does not deny, so a new body is covered without anyone remembering; a body that must stay permissive (a feed shape, a `#[serde(flatten)]`) says so in that test's `UNKNOWN_FIELDS_ALLOWED` with its reason. One consequence: a read body is *not* PUT-able verbatim (it carries the key and the server-owned provenance/derived columns) — `test_support`'s `writable_body`/`NOT_CLIENT_WRITABLE` is what the round-trip tests replay a read through
3. `impl infra::http::CrudEntity for <Model>` — `TABLE`, `COLUMNS`, `NOUN` (+ `KEY_COLUMN`/`ORDER_BY`/`Key` where they aren't `id`/`id`/`i64`). This *is* the list/get-one/delete implementation: the routes use the generic `http::list_handler::<M>` / `get_handler::<M>` / `delete_handler::<M>`, and `http::crud_list`/`crud_get`/`crud_delete` are the query behind them — don't hand-write another `async fn list`/`get_one`/`delete`, and don't spell the SELECT column list out per query. A verb that does more than one table's worth of work (a filtered list, a read that attaches child rows, a delete with referenced-row guards) stays hand-written for that verb only; the entity still implements the trait for the rest
4. `pub db_*` functions — `db_upsert` (always hand-written: this is where the write-time invariants live), plus `db_list`/`db_get`/`db_delete` as one-line delegations to the `crud_*` helpers where other modules or the DB-level tests call them by name. Where only the tests do, gate the wrapper `#[cfg(test)]`; where nothing does, don't write it
5. Private axum handlers — the verbs the trait doesn't cover (`upsert`, operations): call the `db_*` functions and return `Result<_, infra::http::ApiError>` (entity errors convert via their `From<EntityError> for ApiError` impl)
6. `pub fn router() -> Router<SqlitePool>` — registers the entity's routes
7. Inline `#[cfg(test)]` module — DB-level tests and API-level tests via `tower::ServiceExt::oneshot`

A `DELETE` of a row that isn't there always answers `404` with a plain-text body naming it (`no <noun> with that id`) — never a bare `StatusCode::NOT_FOUND`, which the web UI can only show as "HTTP 404". `delete_handler` does this from `NOUN`; a hand-written delete uses `infra::http::deleted(found, noun)`, or its own `ApiError::not_found` where the wording needs the composite key (`exchange_holiday`). `entities::tests::deleting_a_missing_row_is_404_naming_what_was_missing` pins every delete route against that contract — add the new route there.

New entity modules are added by dropping the file in `src/entities/` and adding one `pub mod <entity>;` line plus one `.merge(<entity>::router())` line in `src/entities/mod.rs` — `main.rs` and `app.rs` don't change. Reports follow the same pattern in `src/reports/mod.rs`.

# API conventions
- `GET  /entities`      → 200 JSON array
- `GET  /entities/:id`  → 200 JSON or 404
- `PUT  /entities/:id`  → 204 No Content (upsert)
- `DELETE /entities/:id` → 204 No Content or 404

# Test conventions
- Shared fixtures live in `src/test_support.rs` (`#[cfg(test)]`-declared in `main.rs`): `test_pool()` (in-memory DB, migrations + seed data included) and builder-style row factories — `listing(id)`, `buy/sell/drp(id, listing_id)`, `trade(id, listing_id, type)`, `amma(id, listing_id)`, `income(…)`, `ess_statement(…)` — each starting from a complete default row with setters for what tests vary, a `.with(|x| …)` escape hatch for anything else, and `.insert(&pool)`/`.build()` terminals (inserts go through the entity's own `db_upsert`, so write-time invariants still apply). Never re-declare `test_pool` or spell out a full `Trade`/`Listing`/`AmmaStatement` literal in a test module — a new column is added once, in the builder. Module-specific defaults stay as thin local wrappers delegating to the builders
- `test_pool()` does **not** run the 48 migration files. They are run once per test process into a template database, which is then dumped — schema *and* contents — to one SQL script (`dump_database` in `test_support.rs`, tables → rows → indexes/triggers/views, `sqlite_sequence` restored last); every pool after the first replays that script instead (~4 ms against ~89 ms). `cached_schema_matches_the_migrated_schema` is what makes that safe: it builds one database each way and compares the whole of `sqlite_master` — every table, index, trigger and view, normalised for comments and whitespace — plus each table's rows and the `_sqlx_migrations` rows. Keep that test passing; a cache that silently lost a trigger would switch the audit trail off in every test while the suite stayed green. Two consequences: a migration that changes the schema needs no change here (the template is captured from the live migration set at runtime), and a test of the *migration machinery itself* must not use `test_pool` — `infra::db::tests::pool_migrated_below(N)` builds its pool from `sqlx::migrate!()` directly so one migration can be applied to data that predates it, and stays that way
- API tests drive the router in-process through `test_support::ApiClient` — no network, no port binding, and never a hand-rolled `Request::builder()` (`test_support.rs` is the only file that builds one; a self-test module there pins every verb against the real router). Construct it with `ApiClient::over(router().with_state(pool))` for one module's own routes, or `ApiClient::full(&pool)` for the whole application as `main` serves it — that one injects an offline `QuoteStub`, so no test path can reach the network (`full_with` takes a caller-supplied fetcher). Verbs: `get`/`put`/`post`/`delete`, `put_raw`/`post_raw` for a body already written out as a string, `post_bytes(path, content_type, body)` for the non-JSON payloads (multipart uploads, the CSV/XML import feeds — the content type is `Option` because the import endpoints take a bare `String` body and are driven with none), and `post_empty` for `POST /jobs/{name}`. Each answers an `ApiResponse { status, headers, body }` with `json()`, `text()`, `status_and_body()` and `expect_status()`; `get_json`/`put_json`/`put_ok`/`post_json` fold the status assertion and the decode into one call. Where a module reaches for the same router three or more times, it keeps a one-line local `fn client(pool: &SqlitePool) -> ApiClient` rather than repeating `ApiClient::over(…)`
- DB tests call `db_*` functions directly against the pool
