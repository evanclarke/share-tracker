# Rules
- Only mark a TODO item done when a test exists and passes for it
- Never delete a TODO item. `TODO.md` holds only open / in-flight work; `DONE.md` is the archive of completed and decided (out-of-scope / not-reproducible) sections, split by topic into `DONE/*.md` files (see `DONE.md`'s index/table for which file covers what — it's an unbounded archive, so it doesn't live in one file). When a `## ` section in `TODO.md` is fully closed — every item `[x]`, or the remaining `[ ]` items are explicitly N/A — move the whole section verbatim (heading + items + notes) into the matching `DONE/*.md` file, preserving its text. Archiving is the mechanism for "never delete"; nothing is removed, only relocated
- Solo project: commit directly to `main`. Don't create feature branches for commits
- `cargo build` and `cargo test` must both be warning-free before a task is done (a `pub` item only reached from `#[cfg(test)]` code warns in the non-test build — gate it `#[cfg(test)]` or remove it), `cargo fmt --check` must pass, and `cargo clippy --all-targets -- -D warnings` must be clean — CI and the pre-push hook (`.githooks/pre-push`) both enforce all three, so a task isn't done until all three pass locally, not just build+test
- `cargo test` runs the full suite (2759 tests, ~8s as of 2026-10-11) — still pass an explicit long timeout (900000 ms) rather than the tool default, since a cold `cargo build` of the dependency tree (~2.5 min, see the dev profile below) can precede it. Two build settings plus one test-harness setting keep it there and must not be dropped: `.cargo/config.toml` sets `LIBSQLITE3_FLAGS=SQLITE_DEFAULT_MEMSTATUS=0`, without which SQLite's global allocation-statistics mutex serialises every test thread (the suite took 658s, and got *slower* the more test threads it was given); `Cargo.toml`'s `[profile.dev.package."*"]` builds dependencies — chiefly the bundled SQLite C library — at `opt-level = 2` while this crate stays at 0, so incremental rebuilds stay fast. The third is `test_support::test_pool`'s cached schema (see Test conventions): replaying the 51 migration files cost ~89 ms per pool against ~1500 pools, ~220 s of CPU that the parallelism was hiding behind a 23 s wall clock. Each file carries the reasoning; if the suite ever looks slow again, check all three are still in effect
- Building needs `protoc` on the machine (the `yfinance-rs` dep's build script compiles a protobuf schema): `brew install protobuf` locally, and ci.yml installs `protobuf-compiler` — keep that step if the workflow changes
- CI also gates the dependency tree: `cargo deny check advisories` fails on known RustSec advisories (config + policy in `deny.toml`; run the same command locally — `cargo install cargo-deny --locked`). An advisory with no upstream fix goes on deny.toml's ignore list with a `reason` and a same-line `# expires: YYYY-MM-DD` comment; `doc_checks::advisory_ignores_expire` fails the suite once the date passes, so ignores are always temporary. Dependabot (`.github/dependabot.yml`) raises weekly grouped update PRs for Cargo and GitHub Actions
- Implement a requirement fully: if the spec says "apply the 50% CGT discount", compute the discounted figure — don't stop at an eligibility flag/indicator. If only partially done, leave it unchecked in TODO with a note on what remains
- Recurring background tasks (weekly backup, weekly RBA FX import, monthly imports, future jobs) run via the cron scheduler in `infra/scheduler.rs`: register the work in `registry()` (`infra/scheduler/registry.rs`) and add a line to `schedule.cron`. A schedule line may carry an optional IANA timezone between the cron expression and the job name (`30 17 * * 1-5 America/New_York price-import`) — use the market's own zone for market-close-driven jobs so DST can't shift the margin over the close; no zone means local server time. The scheduler logs the next scheduled run time at INFO after every run (and at startup) — its `next run scheduled` line — so the schedule is verifiable from logs without reading code. Every run also goes through `run_job`, which brackets it with `job started` / `job finished` INFO lines; keep both the scheduled loop and the manual `POST /jobs/{name}` trigger routed through it so no job bypasses the start/finish logging or the per-job lock that serialises runs of the same job (an overlapping trigger waits for the in-flight run, never executes concurrently). `run_job` runs each job on a spawned task, so a manual trigger whose client disconnects does not cancel the run, and a panicking job is recorded as a failed run without ending its schedule loop
- Keep the docs in sync when the data model or HTTP API changes: a new/changed table or column updates `docs/SCHEMA.md` (incl. its Relationships section); a new/changed/removed endpoint, status code, or request/response shape updates `docs/API.md` (incl. its Response codes section); a user-visible feature or scope decision updates the Features or Known limitations list (`README.md` / `docs/API.md`). Doc updates are part of the same task, not a follow-up

# Financial correctness
- ATO reference guidance is mirrored in `docs/ato/` (CGT calculation, the 50% discount and loss-netting order, cost base, AMIT/AMMA cost-base adjustments incl. CGT event E10, LIC deduction, managed-fund income components, the FITO offset limit). Read `docs/ato/OVERVIEW.md` first — it indexes each file and maps it to the relevant calculation. Consult these before implementing or changing any tax rule; the live ATO site (ato.gov.au) is authoritative if a doc looks stale
- To fetch from ato.gov.au use `scripts/ato-fetch.py URL` (add `--examples` for just the worked-example sections) — the site returns 403 to non-browser clients, so the WebFetch tool does not work; the script fetches via curl with a browser User-Agent and strips the HTML to text. The ATO legal-database print view (`https://www.ato.gov.au/law/view/print?DocID=<DOCID>&PiT=99991231235958`) renders a whole publication in one page. Mirror anything you rely on into `docs/ato/` (source URL + retrieval date header) and index it in `docs/ato/OVERVIEW.md`, escaping every `$` in the mirrored prose as `\$` (GitHub renders a pair of them on one line as a LaTeX span, swallowing the quoted text between); that is a rendering escape only, so normalise it back before comparing a mirror against its live page — `doc_checks::ato` is what does that for the tests
- Money and quantities are always `Decimal`, never `f64` — there is no float anywhere in `src`, and `infra::decimal`'s `no_source_file_types_a_money_or_quantity_as_a_float` keeps it that way, scanning the whole tree (comments and string literals stripped by `test_support::code_only`) with the two floats that *refuse* a JSON number allowlisted by reason. New monetary columns are `TEXT`; migrations must preserve precision (never round-trip a value through a `REAL` column)
- `TEXT` decimal columns cross the sqlx boundary through `infra::decimal`'s `Money`/`OptMoney` newtypes in *both* directions: a row struct is `#[derive(sqlx::FromRow)]` with `#[sqlx(try_from = "Money")]` / `#[sqlx(try_from = "OptMoney")]` on its plain `Decimal`/`Option<Decimal>` fields, and a write binds `.bind(Money(x))` / `.bind(OptMoney(x))`. Never hand-write a `FromRow` for a row struct a derive can express, and never `.bind(x.to_string())` (a test scans for it) — the read half is compiler-enforced, since `Decimal` has no `sqlx::Type<Sqlite>` impl of its own. `row_dec`/`row_opt_dec` (same codec, column named by sqlx) are for the two `FromRow` impls a derive *cannot* express — a tagged enum whose payload columns vary by variant (`ActionKind`), a struct with computed fields (`reports::performance::TradeFlow`) — and for ad-hoc row reads; `parse_dec` is for a `String` already in hand. Parse failures always propagate as `sqlx::Error::Decode`; never `.parse().unwrap_or(Decimal::ZERO)` — a silent zero corrupts financial output without failing
- Reports take the Australian-tax view: cost base, proceeds, and income totals are in AUD. Convert every non-AUD amount to AUD using the record's `fx_rate` before aggregating or comparing — never mix currencies in one calculation. A stored `currency` column is read into `infra::currency::CurrencyCode`, never a `String`: it has no `PartialEq<&str>` outside `#[cfg(test)]`, so `currency == "AUD"` does not compile in production code and `CurrencyCode::is_aud()` (over the one rule, `infra::currency::is_aud`, which the FX lookups handed a bare code also call) is the only way to ask
- Market settlement (T+n) counts business days — skip weekends and the exchange's seeded public holidays (`exchange_holidays`, looked up per the listing's exchange via `exchange_holiday::exchange_holidays_for_listing`); never just add calendar days. Exchange-less listings (`security_type = 'Crypto'`, NULL `exchange_mic`) settle same-day instead — no T+n, no holiday calendar (`trade::auto_settlement_date`). The stored `settlement_date` is also the **register** date: entitlement at a corporate action's record date (a return of capital's reduction, a rights issue's entitlement, CGT event C2) asks whether a Buy settled on/before the record date and whether a Sell settled after it — never the trade date, which is off by the ex-date's one business day under T+2

# Data integrity
- A transaction that **writes** is begun with `infra::db::write_tx(pool)` — `BEGIN IMMEDIATE`, which takes SQLite's write lock at the `BEGIN` — never with `pool.begin()`. A deferred `BEGIN` starts as a reader and fails *immediately* when it tries to upgrade after another connection has written (`SQLITE_BUSY` 5 / `SQLITE_BUSY_SNAPSHOT` 517, neither of which `busy_timeout` retries), which is a 500 with an empty body for whoever was writing; queued from the start, the busy timeout applies and a concurrent writer waits its turn. A read-only transaction is begun with `infra::db::read_tx(pool)`: deferred, as a reader should be, and a `ReadTx` with `PRAGMA query_only` on for its duration, so SQLite refuses any write through it (`SQLITE_READONLY`) — the read/write split is the transaction's type, not a file list (`a_read_transaction_refuses_every_write`). `sqlx::Pool::begin` itself is in `clippy.toml`'s `disallowed-methods`, so a stray `pool.begin()` fails `cargo clippy -- -D warnings`; `read_tx` is its one `#[allow]`ed caller. The pool's release hook (`infra::db::connect`) switches `query_only` back off, so a `ReadTx` dropped on an error path cannot hand the next caller a read-only connection — build any new production pool through `connect`. Top-level only: sqlx issues a `SAVEPOINT` for a nested transaction and rejects a custom `BEGIN` there, so a transaction on an existing `&mut *tx` keeps using `.begin()`. Production code never takes a bare pooled connection (`pool.acquire()`) either: a multi-statement write on one autocommits statement by statement and persists half of itself on a failure, and no scan can tell a read from a write, so the rule is the connection's kind — read on a `read_tx`, write on a `write_tx` (`infra::db`'s `production_code_never_writes_on_a_bare_pooled_connection` scans every non-test file; tests may still `acquire`)
- Enforce data-model invariants at write time inside a transaction, not only in reports. A multi-row invariant (e.g. a Sell's parcel allocations must sum to its quantity) must be validated and committed atomically so a partial/invalid state can never be persisted; reject with `422` otherwise. If standalone child-entity writes could reintroduce a bad state, restrict them
- Every field in the data model must be used by a calculation or endpoint, or carry a comment marking it informational-only. Don't leave stored fields silently unused
- Migrations must never drop data: no destructive schema changes — migrate existing rows forward (e.g. the holding-accounts migration moved every row to the seeded default account)
- A field that holds a limited set of values is an enum: CHECK-constrained in the database (and a typed enum where parsed in Rust), never a free-text column
- Every UPDATE/DELETE of an audited table is recorded by the append-only audit trail (`row_history`, migration 0013; inspected via `GET /reports/row_history` and the web UI's Row History screen). The audited-table list lives in three places a test pins together: the migration's CHECK + trigger pairs, `reports::row_history::AUDITED_TABLES`, and the UI table picker in `config.js`. A migration that adds a column to an audited table must DROP and re-CREATE that table's two `*_row_history_*` triggers with the new column list; a new financial fact table needs its own trigger pair plus entries in all three lists. Never UPDATE or DELETE `row_history` itself (its own triggers abort the write) — retention is keep-forever by decision

# Project structure
Modules are grouped into four folders; `main.rs`, `app.rs`, and the migrations live at the `src` root.
- `src/main.rs` — server startup: init pool, build registry, spawn scheduler, serve, graceful shutdown
- `src/app.rs` — `app::router(pool, registry, fetcher)` assembles the application (testable without `main`): `api_routes(base_path, auth)` merges the entity + report + scheduler + web (+ login, with `[auth]`) `OpenApiRouter`s, `split_for_parts` hands back the axum router and the OpenAPI operations generated from those same registrations, and `api_spec::router(generated, …)` completes and serves the document — so a route cannot be served undocumented or documented unserved. The login routes read their `AuthState` as an extension `router` layers on, which is what lets the document be generated without a credential. The price `fetcher` (`closing_price::SharedFetcher`) is injected, not constructed here, and `scheduler::registry(pool, db_path, fetcher)` takes it the same way — the live `YahooFetcher` is built only in `main`, so no test path can reach the network (tests pass `closing_price::test_support::QuoteStub`)
- `src/api_spec.rs` — the generated OpenAPI 3.1 description served at `GET /openapi.json` (non-test production code, deliberately at the `src` root beside `app.rs`). There is no route table: every handler is a `#[utoipa::path(verb, path = "…", summary = "…")]` function registered through `utoipa_axum`'s `routes!` (`OpenApiRouter`), so the route axum serves and the operation documented are one declaration. utoipa reads the rest off the handler itself (Cargo features `axum_extras` + `auto_into_responses`): the request body from its `Json<T>`/`Form<T>` extractor, the success responses from its return type through `utoipa::IntoResponses` (`infra::respond`), and the query parameters from the `params(T)` naming its `Query<T>` type (utoipa drops an `IntoParams` extractor not listed there — the one thing an annotation must repeat; `every_query_parameter_matches_its_summary` checks the summary's `?name=` tokens against the documented set both ways, and `entities::tests::every_list_route_is_classified_for_filtering` each entity list's against `LIST_ROUTES`). A non-JSON request body (a feed import's text, the multipart upload, the login form) is declared in the annotation's `request_body(…)`. The summaries are prose, hand-written beside the handler. `publish` completes the generated operations: the `operationId` derived from verb and path (`operation_id`), the one tag — the `docs/API.md` `## ` section named by the longest matching prefix in `TAGS` (`tag_for`; a new top-level path segment needs a `TAGS` row, and the tag test fails until it has one) — a required string path parameter per `{name}` segment, the non-success responses (`non_success_responses`: `422`/`413`/`415` for a body, `404` for a path parameter, `502` for an import/fetch, `500` always), request-body descriptions, one operation per `/static/*.js` module from `web::JS_MODULES` (the loop no annotation can describe), the handler's doc comment dropped (it is written for the code's reader), `servers` (the deployment's prefix), and `securitySchemes` + a global requirement when `[auth]` is configured (without it no `/login`/`/logout` route is merged, so none is documented). `router(generated, base_path, auth)` completes and serialises it once, and also serves the agent-sized pieces: `GET /openapi/index` (`route_index`, one line per operation, read from the published document) and the `?tag=`/`?operation=` slices (`slice_where` — the kept operations plus the schemas they reach through every `$ref`, pinned self-contained for every tag and every operation). `every_route_is_registered_through_routes` fails on a route registered with axum's plain `.route(…)` (served, undocumented) outside the two classified sites (the JS-module loop, the base-path redirect). Schemas come from the real `#[derive(utoipa::ToSchema)]` structs — a field's `///` doc comment is its published `description`, and `every_request_body_property_is_described` requires one on every property a request body reaches, so a new body field needs its comment; the `components!` list registers every type a handler takes or answers (and implements `infra::respond::Component` for it, so a response type missing from the list does not compile), `components()` merges them with a `BTreeMap`, and the uniqueness test is what pins a name reached by two different schemas
- `src/ato_examples.rs` — `#[cfg(test)]`-only acceptance tests reproducing the worked examples in the ATO docs (`docs/ato/`): each test cites its doc + example, enters the facts purely via the HTTP API (full `app::router`), and asserts the ATO's stated figures. Add a test here when a new feature makes another doc example representable
- `src/doc_checks.rs` — `#[cfg(test)]`-only tests pinning documentation-only requirements (a TODO item is only done with a passing test, including doc-only items): each asserts its required text — e.g. a Known-limitations entry and the QC header of the ATO doc it cites — is present in `docs/API.md`/README via `include_str!`. Add a test here when a requirement is satisfied by documentation alone. One test in the file is structural rather than textual: `every_markdown_link_resolves` walks **every** `.md` in the repo at runtime and fails on a relative link whose file is missing or whose `#fragment` names no heading — the archive is maintained by *moving* whole sections between files, and a link written relative to the repo root breaks when its section lands in `DONE/` (`docs/API.md` becomes `../docs/API.md`). Anchors are compared on GitHub's `github-slugger` rule, which does **not** collapse repeated separators: an em dash is stripped and leaves both surrounding spaces, so `## A — B` is `#a--b`, not `#a-b`. A moved section fixes its own links; a bold lead-in like `**Ticker or name changes:**` is not a heading and cannot be linked as one
- `src/infra/` — cross-cutting infrastructure (`mod.rs` re-exports each):
  - `infra/db.rs` — pool init (runs migrations), `write_tx` (the `BEGIN IMMEDIATE` every write transaction is begun with — see Data integrity), `WriteMode` (how a computed write's transaction ends: `finish` commits it, or rolls it back for the `?dry_run=true` preview that `infra::http::DryRunQuery` decodes — the ten previewable writes call it where they used to call `tx.commit()`, and their handlers answer `infra::respond::Written<T>` (`200` for the preview, `201` for the write, both documented from the type); `ApiClient::assert_dry_run_previews`/`assert_dry_run_refuses_alike` pin a new one), weekly DB backup (`backup`/`backup_path`): each fresh backup is verified (`PRAGMA integrity_check` + migrations match the live DB; a bad file is quarantined as `<name>.db.bad` and the job fails loudly), then the destination is pruned to the retention policy (newest 8 + first-of-month keepers for the 12 most recent months; only pattern-matched backup files of this database are ever deleted). Off-machine copies are deliberately a documented external step (README "Off-machine copies"), not a job
  - `infra/args.rs` — CLI args: `--db` (default `share-tracker.db`), `--port` (default 3000), `--schedule`
  - `infra/config.rs` — server configuration: an optional TOML config file merged with CLI args (precedence CLI flag > config-file value > built-in default). The file is loaded from `DEFAULT_CONFIG_PATH` (`/usr/local/etc/share-tracker.toml`, where the FreeBSD package installs it) unless `--config PATH` names another, which must then exist; unknown keys and invalid TOML abort startup rather than silently falling back to a default database. `Settings::resolve` folds `args::Args` + `ConfigFile` into the resolved `Settings` and normalises `base_path` (a URL path prefix, `""` at the root); the `[auth]` and `[email]` tables are config-file only because a password on the command line is visible to anyone on the host via `ps` (see `infra::auth` / `infra::email`)
  - `infra/logging.rs` — tracing subscriber init; reads `RUST_LOG`, defaults to `info`
  - `infra/decimal.rs` — the `Money`/`OptMoney` TEXT⇄`Decimal` sqlx codec (`Type`/`Decode`/`Encode` for Sqlite), plus the `parse_dec`/`row_dec`/`row_opt_dec` helpers over it, and the two pieces of shared arithmetic: `mul_div` (*the* multiply-then-divide pro-rate) and `apportion(whole, num, den) -> (share, rest)`, *the* two-way split of a cost base whose halves add back to `whole` exactly — every split whose halves land in different places (a demerger's two legs, a partial rollover's carried scrip share and the realised-gains report's cash share) takes its half from it, never `whole − mul_div(…)`, which rounds on a 28-digit pro-rated cost base. The **outbound** JSON rule is pinned by `infra::decimal`'s `a_money_field_serializes_as_a_json_string`/`every_money_field_of_a_serialized_row_is_a_json_string` tests and `api_spec`'s no-JSON-number walk over every component schema — not by a Cargo feature: `serde-str` gates only `Deserialize`, so the string `Serialize` is what `rust_decimal` does while `serde-float` is off
  - `infra/currency.rs` — `CurrencyCode`, the serde/sqlx-transparent newtype every `currency` column and field is typed as (a string in the OpenAPI document, the `CurrencyCode` component); see Financial correctness for the `is_aud` rule it carries. Also `Aud`, a `Decimal` known to be in AUD: `fx::apply_rate_to_aud` makes one by converting, and `Aud::stated` — which vouches that a bare figure is already AUD — is allowed only in the files `AUD_STATED_ALLOWED` names with their reason (the request `prices` maps, read by `infra::decimal::strict_aud_map`, and the activity ledger's `price`). Live quotes (`LiveValuation::aud_price`), stored valuations and every report's price map carry it. `Aud` is also the marker of `domain::cost_base::CostBase<C>` against `Native`: the pipeline yields a `CostBase<Native>` and `into_aud_with` is the only way to a `CostBase<Aud>` (the marker field is private), which is what open parcels, indexation and every AUD report take — so a native breakdown can neither be reported as AUD nor converted twice, which an AUD fixture's rate-1 pass-through could never catch
  - `infra/id.rs` — typed row ids (`ListingId`, `HoldingAccountId`, `TradeId`, via the `id_type!` macro): serde/sqlx-transparent newtypes over the integer key, so the JSON and the SQL binds are unchanged and the OpenAPI document gains an integer component per id; no conversion between two id types is implicit, `.0` is the deliberate escape for generic plumbing (`insert_with_optional_id`, the audit trail's `row_id`). One field is deliberately left bare: `realised_gains::RealisedGainLoss::sale_trade_id` (and the tax report's `DisposalParcelRow` copy) is a *trade* id for a `Sell` row but a `rights_sales` id for a `RightsSale` row, so it stays `i64` and every consumer reads it as a `TradeId` only after checking `source`. A map keyed by listing is `HashMap<ListingId, _>` (by holding, `(ListingId, HoldingAccountId)`), never `HashMap<i64, _>`. Test-only `PartialEq<i64>` lets an assertion compare against a literal; the `test_support` builders keep taking plain integers and convert inside
  - `infra/date.rs` — the shared "as-of" cutoff helpers: `open_ended_cutoff()` is the sentinel no-upper-bound date (`9999-12-31`, lexicographically maximal as the `YYYY-MM-DD` TEXT the SQL compares — deliberately not `NaiveDate::MAX`, whose `+262143-12-31` rendering sorts *before* the digits); `as_of_or_open` resolves `None` to that sentinel for reads whose job is "every recorded fact", while `as_of_or_today` resolves it to `today()` for a **live** view — the two deliberately disagree, so a live holdings read must reach for the latter
  - `infra/fx.rs` — AUD conversion via the ATO/RBA reference rate (per-trade `fx_rate` fallback): `FxRates` pre-loads the whole rate table so report loops convert from memory — reports load it once (inside their read transaction) instead of one DB lookup per row (the pool-based `to_aud`/`resolve_rate` twins are `#[cfg(test)]`, kept to pin that both paths resolve identically). `resolve_valuation_rate` (pool and `FxRates` forms) is the **valuation-only** fallback: when the valuation month's rate isn't imported yet it substitutes the most recent earlier month's (≤ 2 months back) and flags the result provisional — only snapshot generation, live-quote conversion, and the period-performance report's FX attribution (`reports::period_performance`, over `reports::valuation::stored_valuations`) may call it, and the caller must surface the flag (snapshot `provisional`, row `fx_provisional`, period-performance `provisional`); tax calculations and FY reports stay on the strict path so no tax figure is ever computed from a fallback-month rate
  - `infra/fetch.rs` — the shared bounded feed-fetch layer every published-feed import goes through: `fetch_feed` bounds the whole call with `FEED_TIMEOUT` (30 s, applied both as the `reqwest` client timeout and a `tokio::time::timeout` over the `FeedFetcher` seam, which is what makes the stalled path testable without a socket) and the body with `MAX_FEED_BYTES` (16 MiB), so a stalled or oversized response can no longer park the request task or buffer an unbounded body. It also owns the failure rendering: `cause_chain` walks an error's whole `source()` chain so the recorded `ImportError::Fetch` says *why* (a `reqwest::Error`'s own `Display` names only the URL — SCENARIOS T-06), and `FetchError` carries that rendering into `job_runs.error`, the health banner and the server log
  - `infra/email.rs` — outbound email: `Document`/`Section`/`Table` describe a message once and `Document::render` produces both parts of its `multipart/alternative` body (an HTML part laid out like the screen the figures come from, and a plain-text one saying the same thing — writing them twice is how they drift); the `Mailer` trait is the transport seam, injected as a `SharedMailer` built only in `main` so no test path can reach a mail server (tests use the in-process `Outbox` double), with `SmtpMailer`/`EmailSettings`/`Notifier` over `lettre`. Email is optional: absent the config file's `[email]` table there is no mailer at all, and the weekly-summary and price-alert jobs record a run that succeeded while sending nothing
  - `infra/http.rs` — `ApiError`, the one error type every handler returns (`Result<_, ApiError>` + `?`): `Internal` responds 500 with an empty body and logs the wrapped error via `tracing::error!` when the response is built — never `map_err(|_| StatusCode::…)`, which swallows the cause; `Unprocessable`/`BadRequest`/`not_found(msg)` carry the plain-text reason the web UI shows. `From<sqlx::Error>` classifies DB constraint violations as 422 with the rephrased constraint message — its foreign-key wording is the **write** direction ("the request refers to a record that does not exist"), and it reads a constraint violation as the *client's* fault, so a write whose every value the server composed (a `report_snapshots` row) maps its errors through `ApiError::from_server_write` instead, where a violation is the logged `500` it is; likewise a DELETE must never reach that arm: a delete fails the same FK for the opposite reason (the row is there and something depends on it) and classifies the violation itself via `fk_dependants_message`, which discovers the blocking tables from `PRAGMA foreign_key_list` and answers a 422 naming each with its row count. `delete_handler` does this for every `CrudEntity`; a hand-written delete with its own outcome enum carries the ready-made body in a `StillReferenced(String)` variant so the wording still lives in the `From<EntityError> for ApiError` arm (see `entities::corporate_action::db::DeleteError`). Per-entity error enums stay and convert via `impl From<EntityError> for ApiError` beside the enum — handlers never match error variants themselves. Every error enum in the tree is `#[derive(thiserror::Error, Debug)]` with an `#[error("…")]` per variant, `#[from]` on its `Db(sqlx::Error)` variant (so `?` converts and never a hand-written `impl From<sqlx::Error>`), and `#[source]` on a variant wrapping another error enum — that keeps the underlying failure's own message in `Display` and reachable through `source()` when the enum ends up inside `ApiError::Internal`. The `#[error]` strings are **log** wording, deliberately not the user-facing 422 bodies: those live in the `From<EntityError> for ApiError` arms, which `docs/API.md` documents and per-entity rejection tests pin. One `From<sqlx::Error>` impl stays hand-written for a stated reason — `ApiError`'s (it classifies constraint violations, a busy database, and a boxed `FxError` rather than wrapping). The three report enums (`reports::valuation`/`snapshot`/`period_performance`) follow the derive convention like every other enum — `Db(#[from] sqlx::Error)` keeps the database failure (and any `FxError` boxed into a decode error) downcastable by `ApiError::from` to the documented `422`, with a separate `Failed(String)` arm for their genuinely non-sqlx failures
  - `infra/respond.rs` — the success types a handler returns, each carrying its status (and, for a non-JSON payload, its media type) so the OpenAPI document reads them off the signature (`utoipa::IntoResponses`): `Json<T>` (200), `Created<T>` (201), `Written<T>` (a previewable write: 200 for `?dry_run=true`, 201 otherwise), `UpsertResponse<T>` (201/204), `NoContent` (204), `SeeOther` (303), and `Payload<M>` (a 200 whose body is a page, stylesheet, CSV export or stored file — `M` is the `MediaType`: `Html`, `Css`, `Csv`, `PlainText`, `OctetStream`, `JavaScript`). A handler never returns a bare `StatusCode`, a `(StatusCode, Json<T>)` tuple or a hand-built `Response` — none can say which status it answers, and with `auto_into_responses` none compiles. A JSON body is described as a `$ref` through `JsonBody`, implemented for every `Component` (the `api_spec` `components!` list) and a `Vec` of one. `ApiError` documents nothing here: the non-success responses depend on the route, so `api_spec` adds them per operation
  - `infra/extract.rs` — the `Query`/`Json` extractors every handler takes in place of axum's: a request the decoder cannot read is refused in one shape on every route — `cannot read the query string: <serde reason>` (always `400`) / `cannot read the request body: <serde reason>` (axum's own status: `422` data, `400` syntax, `415` content type, `413` length). `Json` is also the response wrapper. `no_handler_takes_axums_own_query_or_json` scans `src` and fails on any import of axum's `Json`/`Query`, so never map an extractor rejection by hand in a handler
  - `infra/auth.rs` — optional shared-credential access control, disabled unless the config file's `[auth]` table is present (then `require_auth`, applied in `app::router`, gates every route except the small allowlist the login page itself needs — `GET`/`POST /login` and `GET /static/style.css`). This is access control only, not multi-tenancy: one username + Argon2 password hash, plus an optional `Authorization: Bearer <api_token>` for the deployment scripts. The session cookie is self-contained — `<hex(username|expiry)>.<hex HMAC-SHA256>` keyed off the password hash, so there is no session table and no migration; changing the password invalidates every session, and `POST /logout` can only tell the browser to drop the cookie (a copied-out value stays valid until its 30-day expiry). `auth/login.html` (templated with `{{BASE}}`/`{{THEME}}`/`{{ERROR}}`) is the whole sign-in UI. `POST /login` also carries a **bounded per-source failed-login lockout** (`LockoutTracker`): a failure streak counted at the gate — the attempt is reserved before the Argon2 verify, so concurrent guesses cannot race past the budget — keyed on the peer's IPv4 address or IPv6 **/64 prefix** (never the port), hard-capped at 4096 sources, with a process-wide ceiling of 100 failed attempts an hour across every source above it (reaching it refuses every password sign-in, the owner's too — sessions and the bearer token are unaffected), with the failure window idle-based, `Retry-After` rounded up, and a refusal answered `429` whatever the client's `Accept` header says. `main` must serve with `into_make_service_with_connect_info::<SocketAddr>()` for the peer to be there at all; without it every request shares the one documented `<unknown peer>` bucket
  - `infra/request_guard.rs` — the request guard `app::router` layers outside every route (inside only the security-header layer and the panic net), whatever `[auth]` says: an unsafe method a browser marks cross-site (`Sec-Fetch-Site` other than `same-origin`/`none`, or an `Origin` that does not name the `Host`) is refused `403`, because bodyless operations, the text-body feed imports and the multipart upload are reachable from a plain cross-site `<form>`; and with no `[auth]` a `Host` that is not `localhost`, an IP literal or a config-file `allowed_hosts` name is refused `403` (DNS rebinding). A client sending neither header (curl, scripts, Claude Code) passes. `ApiError::Forbidden` is the shape
  - `infra/security_headers.rs` — the browser-hardening response headers, layered (`map_response`) outside the request guard so refusals carry them too: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and a `default-src 'self'` CSP with `frame-ancestors 'none'` whose `script-src` allows the one inline script, `web::THEME_BOOT_SCRIPT`, by a SHA-256 hash computed from that const at startup — so editing the script needs no policy change, but a *new* inline script (or a `style=` attribute in markup; CSSOM `el.style.x =` writes are fine) would be blocked. The layer only fills headers a handler left unset: the attachment content route answers `SAMEORIGIN` / `frame-ancestors 'self'` because the edit form's document pane frames it
  - `infra/scheduler.rs` — maintenance-job registry, cron parsing/spawn, inspection routes. Split the same way as `trade.rs`: the parent is re-exports (every `scheduler::X` path preserved, test-only ones behind `#[cfg(test)]`) plus the inline test module, over `src/infra/scheduler/` — `registry.rs` (what each job name does, plus `JobParams`/`RegisteredJob`/`JobTrigger`; add a job with one `register(&mut jobs, "name", …)` call taking an async closure — or `register_manual` for a deliberately schedule-less one-off repair — never by hand-rolling the `Arc`/`Box::pin` wrapping. `register` means the job expects a line in `schedule.cron`, and `schedule::spawn` warns at startup when it has none; `register_manual` records the opposite intent so that warning only ever means a lost line, and `GET /jobs` carries the same flag as `trigger`), `schedule.rs` (`parse`/`spawn` over `schedule.cron`), `run.rs` (`run_job`, the per-entry timer loop, `next_run`), `db.rs` (the bounded `job_runs` history), `http.rs` (`GET /jobs`, `POST /jobs/{name}`)

It is the **lower layer**: entities and reports call into it, and its production code reaches nothing in `entities` (`domain::tests::domain_depends_on_nothing_in_entities` scans for it, test modules exempt) — a loader the pipeline needs lives here (`domain/adjustments.rs`, the ROC/split/price-basis events derived from corporate actions with their loaders and re-basing math, re-exported from `entities::corporate_action`; `cost_base::db_cost_base_reduction_events`/`reduction_for`, the AMIT reduction loader; `open_parcels::db_parcel_sales`/`db_sales_by_parcel`, the allocation reads; `tax_year::amit_in_tax_year`), and where a domain rule needs a fact an entity type carries it takes the fact, not the type (`deduction_destination`'s `debt_deduction: bool`, from `ExpenseType::is_debt_deduction`). `domain/cost_base.rs` is *the* adjusted-cost-base pipeline (initial cost pro-rated to the costed units → AMIT per-unit reduction over the units the adjustment row covers, per CGT event E10 → return-of-capital per-unit reduction per G1, split-aware, both floored at nil → AUD conversion at the acquisition month via `CostBase::into_aud_with` over pre-loaded `infra::fx::FxRates`), carrying the ATO citations; the realised/unrealised/portfolio/open_parcels reports and the scrip-exchange/demerger/transfer operations all call it — never re-implement the pipeline inline. Both reductions are stated **per unit**, so the caller must say what became of the units it is costing: `adjusted_cost_base`/`adjustment_detail` take a `Held` enum (`AsAt(Option<date>)` for units still held, `DisposedOn(date)` for a sale allocation), which bounds the payments they were held for *and* decides which side of an AMMA statement's year end they sit on — never collapse the two back into one `Option<NaiveDate>`. Quantities are typed by unit basis the same way: `adjustments::AcquiredUnits` is a count in one parcel's own as-acquired basis (`ParcelRow`/`Parcel::quantity`, the pipeline's `units`, the AMIT event's counts) and `adjustments::UnitsAt` a count in the basis in force at the date it carries (a sale allocation — `open_parcels::UnitsConsumed::quantity` — or `OpenParcel::remaining_as_of`); `split_adjusted_quantity`/`as_acquired_quantity`/`sold_in_acquired_units` and `UnitsAt::rebased` are the only conversions, and they re-base in either direction, so an allocation cannot be subtracted from a parcel or costed without being re-based first. `.get()`/`.quantity()` is the escape for output and for arithmetic within one basis — never add two parcels' `AcquiredUnits` together Its `ParcelRow` is the shared `FromRow` mapping of a Buy/DRP trade row — reports select `ParcelRow::columns()` (or `columns_qualified(alias)` where the query joins another table) rather than re-mapping trade columns field-by-field; the list is a function, not a column const, because the mapping's last two fields are derived rather than selected — a demerger's head listing, off `corporate_actions`, which is what tells its head replacement parcel from its spun-off one, and `registered_from`, a recursive walk back up the rollover chain to the date the units joined this listing's register — and a caller that selected only the `trades` columns would silently lose both, each of them a return-of-capital entitlement bug. `domain/open_parcels.rs` is the loader *around* that pipeline: `load(conn, as_of)` reads the Buy/DRP rows, the sale allocations, the AMIT/ROC/split events and `FxRates` on the caller's own connection (so it composes into the report's single-snapshot read transaction), drops the fully consumed parcels and returns each open parcel's `ParcelRow` + remaining quantity in `as_of`'s unit basis + AUD `CostBase` — every open-holdings view (portfolio overview, unrealised gains, the open-parcels schedule) is built on it, and a new one must be too rather than re-assembling the read. Its `db_units_sold(conn, as_of)` is the allocations read on its own, for the walks that need per-sale dates instead of a remainder (performance, the net-capital-gain report's per-cohort E10/G1/C2 walk, and `cost_base::db_cost_base_reduction_events`, which needs the units disposed of by each statement's year end). `domain/rollover.rs` is the shared read side of the three parcel-substituting *operations* (scrip exchange, demerger, transfer), which are not built on `open_parcels` because a replacement parcel carries its cost base forward in the original's own currency, not AUD: `CostBaseInputs::load(conn, listing_id)` + `carried_cost_base`/`open_parcels` (the per-listing remaining-units walk over `domain::cost_base`), plus the rollover-chain walks (`source_ancestors`/`replacement_descendants`); their write side is `entities/rollover.rs` — `closing_sell_body`, `insert_replacement_buy` with its `Provenance` column enum, and `created_trades` — which re-exports `CostBaseInputs`/`RolledParcel` so an operation imports the one module. A new operation of that shape uses these rather than growing its own copy of the walk or the INSERT. Its closing Sell goes through `sell::upsert_sell_in_tx(conn, SellWrite { .. })`, whose `provenance` is the twin enum on that side (`sell::SellProvenance`, two variants wider — a buy-back participation and a worthless-shares recognise close parcels without substituting any): a Sell belongs to exactly one operation, so a new one adds a variant to it and to the INSERT's column mapping rather than another `Option<i64>` parameter. `domain/tax_year.rs` holds `tax_year_for` — *the* Australian financial-year bucketing rule (July = next FY, identified by the calendar year of its 30 June end); every FY-keyed report (tax summary, net capital gain, E4 cross-check) uses it — never re-derive `month() >= 7` inline — and `fy_start`, the 1 July that year began (an AMMA statement's income-year window: the AMIT-row write cap, the spill split, the cross-check's coverage band)

# Domain entity module pattern
Each entity in `src/entities/<entity>.rs` follows this structure:
1. Model struct — derives `Serialize`, `Deserialize`, `sqlx::FromRow`
2. Input body struct — for PUT endpoints; omits the primary key (comes from URL path) — and carries `#[serde(deny_unknown_fields)]`, as **every** struct deserialised from an inbound request does (`Json`/`Query`/`Form` bodies, report requests, operation bodies): a misspelt field name must be a `422` naming it, never a silently-ignored default writing a zero into a tax figure. `infra::http::tests::every_request_body_denies_unknown_fields` walks every type reachable from a handler's extractor and fails on one that does not deny, so a new body is covered without anyone remembering; a body that must stay permissive (a feed shape, a `#[serde(flatten)]`) says so in that test's `UNKNOWN_FIELDS_ALLOWED` with its reason. One consequence: a read body is *not* PUT-able verbatim (it carries the key and the server-owned provenance/derived columns) — `test_support`'s `writable_body`/`NOT_CLIENT_WRITABLE` is what the round-trip tests replay a read through
3. `impl infra::http::CrudEntity for <Model>` — `TABLE`, `COLUMNS`, `NOUN` (+ `KEY_COLUMN`/`ORDER_BY`/`Key` where they aren't `id`/`id`/`i64`). This *is* the list/get-one/delete implementation: the routes are one-line `http::crud_list_route!(fn_name, Model, Filter, "/path", "summary")` / `crud_get_route!(…, Key, …)` / `crud_delete_route!(…, Key, …)` instantiations — each writes the concrete `#[utoipa::path]` wrapper over the generic `http::list_handler::<M>` / `get_handler::<M>` / `delete_handler::<M>` (an annotation cannot describe a generic function), with the model, filter and key as identifiers in scope — and `http::crud_list`/`crud_get`/`crud_delete` are the query behind them — don't hand-write another `async fn list`/`get_one`/`delete`, and don't spell the SELECT column list out per query. A verb that does more than one table's worth of work (a filtered list, a read that attaches child rows, a delete with referenced-row guards) stays hand-written for that verb only; the entity still implements the trait for the rest. Its `type Filter` is the query parameters that entity's list accepts: a `#[serde(deny_unknown_fields)]` struct implementing `CrudListFilter`, whose `apply_filter` narrows the query through an `infra::http::FilterClauses` handle (`.eq` / `.date_range`). The handle's `QueryBuilder` is **private**, which is what makes bind-not-interpolate structural rather than conventional — there is no method by which a filter *value* can reach the SQL text, so a new clause shape is added to `FilterClauses` once (and the two hand-written filtered reads, `closing_price::db_list` and `reports::snapshot`'s date-ranged reads, go through `FilterClauses::over` for the same reason)
4. `pub db_*` functions — `db_upsert` (always hand-written: this is where the write-time invariants live), plus `db_list`/`db_get`/`db_delete` as one-line delegations to the `crud_*` helpers where other modules or the DB-level tests call them by name. Where only the tests do, gate the wrapper `#[cfg(test)]`; where nothing does, don't write it `db_upsert` returns `infra::http::Upserted<T>` = `(Upsert, Option<T>)`: the outcome, and for a **create** the stored row read **inside the write's own transaction** (just before `commit`), which the handler passes to `http::upsert_response` — reading it back after the commit let a concurrent DELETE turn a committed create into a 500, or made the `201` report another writer's row. The same rule applies to every operation that returns created rows (`transfer`/`scrip_exchange`/`demerger` build their group before `commit`, not from a pooled `db_get` after it) — and a `?dry_run=true` preview depends on it, since a read after its rollback finds nothing
5. Private axum handlers — the verbs the trait doesn't cover (`upsert`, operations): each annotated `#[utoipa::path(verb, path = "…", summary = "…")]` (plus `params(T)` for a `Query<T>` extractor), calling the `db_*` functions and returning `Result<_, infra::http::ApiError>` whose success type is an `infra::respond` one (entity errors convert via their `From<EntityError> for ApiError` impl)
6. `pub fn router() -> OpenApiRouter<SqlitePool>` — registers the entity's handlers with `.routes(routes!(a, b))`, one `routes!` per path (it registers every handler it names on each of their paths, so never mix two paths in one call)
7. Inline `#[cfg(test)]` module — DB-level tests and API-level tests via `tower::ServiceExt::oneshot`

A `GET`-one or `DELETE` of a row that isn't there always answers `404` with a plain-text body naming it (`no <noun> with that id`) — never a bare `StatusCode::NOT_FOUND`, which the web UI can only show as "HTTP 404" and a client cannot tell from a mistyped path (`ApiError` has no empty 404 at all). `get_handler`/`delete_handler` do this from `NOUN`/`KEY_COLUMN`; a hand-written GET-one names its own key the same way; a hand-written delete uses `infra::http::deleted(found, noun)`, or its own `ApiError::not_found` where the wording needs the composite key (`exchange_holiday`). `entities::tests::deleting_a_missing_row_is_404_naming_what_was_missing` pins every delete route against that contract — add the new route there.

New entity modules are added by dropping the file in `src/entities/` and adding one `pub mod <entity>;` line plus one `.merge(<entity>::router())` line in `src/entities/mod.rs` — `main.rs` and `app.rs` don't change. Reports follow the same pattern in `src/reports/mod.rs`.

# API conventions
- `GET  /entities`      → 200 JSON array
- `GET  /entities/:id`  → 200 JSON, or 404 whose plain-text body names the missing row (`CrudEntity::missing_row_body`, shared with DELETE — `no <noun> with that <key column>`); every handler 404 carries a reason, so an empty 404 means only that no route matched the path. `api_spec`'s `every_get_one_route_names_the_missing_row_in_its_404` walks every GET-one
- `PUT  /entities/:id`  → 201 Created with the created row when the id was free, 204 No Content when it replaced one (`infra::http::upsert_response`; the two deliberate single-status PUTs are `/transfers/:id` always 201 and `/rba_fx_rates/:id` always 204). The create-vs-replace decision runs inside the write's own `write_tx`, and every PUT route is classified in `entities::PUT_ROUTES`, which the OpenAPI pin reads
- `POST` → `201 Created` only when the call created a new resource and its body **is** that resource (a GET-served row, or a group of rows one operation created — `api_spec`'s `CREATED_GROUPS`); a batch summary, a replace or a preview answers `200`, nothing to return `204`. `every_201_post_answers_the_resource_it_created` pins it
- `DELETE /entities/:id` → 204 No Content, or 404 whose plain-text body names what was missing (`CrudEntity::missing_row_body`). A delete blocked by a dependant is 422 naming each blocking table and its row count
- Error responses are never JSON: a rejected request carries a `text/plain; charset=utf-8` reason or is deliberately empty (axum's 404 for a path no route matches, 405, and internal 500). The status/body matrix is `docs/API.md`'s Error-body contract; `infra::http`'s one `error_cases` table is the code side both it and the generated `GET /openapi.json` description derive from
- `GET /openapi.json` serves the generated OpenAPI 3.1 description (`src/api_spec.rs`), behind `[auth]` like every other route. Paths, verbs, request bodies, query parameters and success responses come from the `#[utoipa::path]` handlers themselves; schemas from the real `#[derive(utoipa::ToSchema)]` structs

# Test conventions
- Shared fixtures live in `src/test_support.rs` (`#[cfg(test)]`-declared in `main.rs`): `test_pool()` (in-memory DB, migrations + seed data included) and builder-style row factories — `listing(id)`, `buy/sell/drp(id, listing_id)`, `trade(id, listing_id, type)`, `amma(id, listing_id)`, `income(…)`, `ess_statement(…)` — each starting from a complete default row with setters for what tests vary, a `.with(|x| …)` escape hatch for anything else, and `.insert(&pool)`/`.build()` terminals (inserts go through the entity's own `db_upsert`, so write-time invariants still apply). Never re-declare `test_pool` or spell out a full `Trade`/`Listing`/`AmmaStatement` literal in a test module — a new column is added once, in the builder. Module-specific defaults stay as thin local wrappers delegating to the builders
- `test_pool()` does **not** run the 51 migration files. They are run once per test process into a template database, which is then dumped — schema *and* contents — to one SQL script (`dump_database` in `test_support.rs`, tables → rows → indexes/triggers/views, `sqlite_sequence` restored last); every pool after the first replays that script instead (~4 ms against ~89 ms). `cached_schema_matches_the_migrated_schema` is what makes that safe: it builds one database each way and compares the whole of `sqlite_master` — every table, index, trigger and view, normalised for comments and whitespace — plus each table's rows and the `_sqlx_migrations` rows. Keep that test passing; a cache that silently lost a trigger would switch the audit trail off in every test while the suite stayed green. Two consequences: a migration that changes the schema needs no change here (the template is captured from the live migration set at runtime), and a test of the *migration machinery itself* must not use `test_pool` — `infra::db::tests::pool_migrated_below(N)` builds its pool from `sqlx::migrate!()` directly so one migration can be applied to data that predates it, and stays that way
- API tests drive the router in-process through `test_support::ApiClient` — no network, no port binding, and never a hand-rolled `Request::builder()` (`test_support.rs` is the only file that builds one; a self-test module there pins every verb against the real router). Construct it with `ApiClient::over(router().with_state(pool))` for one module's own routes, or `ApiClient::full(&pool)` for the whole application as `main` serves it — that one injects an offline `QuoteStub`, so no test path can reach the network (`full_with` takes a caller-supplied fetcher). Verbs: `get`/`put`/`post`/`delete`, `put_raw`/`post_raw` for a body already written out as a string, `post_bytes(path, content_type, body)` for the non-JSON payloads (multipart uploads, the CSV/XML import feeds — the content type is `Option` because the import endpoints take a bare `String` body and are driven with none), and `post_empty` for `POST /jobs/{name}`. Each answers an `ApiResponse { status, headers, body }` with `json()`, `text()`, `status_and_body()` and `expect_status()`; `get_json`/`put_json`/`put_ok`/`post_json` fold the status assertion and the decode into one call. Where a module reaches for the same router three or more times, it keeps a one-line local `fn client(pool: &SqlitePool) -> ApiClient` rather than repeating `ApiClient::over(…)`
- DB tests call `db_*` functions directly against the pool
- An invariant that should hold for *every* input — a split that adds back, quantities conserved across any history of writes — is a `proptest` property beside the hand-picked cases, in a `mod properties` inside the module's tests. A property over the database runs each case as `test_support::block_on(async move { … Ok(()) })?` on its own `test_pool()`, under `#![proptest_config(test_support::db_proptest_config())]` (32 cases; `PROPTEST_CASES=2000` overrides it for a deep run); `test_support::parcel_costs`/`insert_parcel_costs` are the shared parcel strategy. Compare figures per parcel, not as sums — a sum of several 28-digit `Decimal`s itself rounds. `proptest-regressions/` (the seeds of past failures, replayed first) is committed
- A concurrency test waits on an **event**, never a fixed `sleep` grace period: `test_support::await_condition` polls a condition with a 10 s deadline. A test whose point is that a write *waits* for another connection's write lock takes `race_pool_with_busy_probe` (a `race_pool` whose connections carry a counting `sqlite3_busy_handler` keeping `BUSY_TIMEOUT`'s contract — test-only FFI over the `libsqlite3-sys` dev-dependency, kept in step with sqlx; production code stays free of `unsafe`) and waits on `BusyProbe::blocked`. The same shape elsewhere: the scheduler's per-job lock counts a blocked acquisition (`RegisteredJob::blocked`), and the login lockout's tests move the tracker's clock (`LockoutTracker::advance`) instead of waiting out a cooldown
